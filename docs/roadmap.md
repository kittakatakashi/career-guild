# ロードマップ

最終更新: 2026-10-18 / ステータス: ドラフト v0.2（Before/After 実験の後ろ倒し、未決事項の追加）

## 1. 目的

このプロジェクトには2つの目的がある。

1. **プロダクト**：経歴書RPG（職務経歴書 → AI査定 → RPGステータス画面）を作って公開する
2. **開発プロセス**：Claude Code を使ったAI駆動開発を、MVPから本格運用まで一通り実践し、**企業のエンジニア向けに実体験として語れる状態**になる

優先度は 2 > 1。プロダクトは「プロセスを体験するための舞台」として扱う。ただし作るものは本物として作る（舞台がハリボテだと、体験もハリボテになる）。

### 1.1 語れるようになりたい領域（優先順）

| 優先 | 領域 | ゴール（このプロジェクト終了時に語れること） |
|---|---|---|
| ◎ | **ガードレール** | CLAUDE.md・permissions・hooks・共有コマンド/skills・plugin で「AIに任せる範囲」をどう設計し、導入前後で何が変わったか |
| ◎ | **自動化** | GitHub Actions 連携、Issue→PR の自動化、ヘッドレス実行、定期実行で「人が張り付かない開発」をどこまで作れたか |
| ○ | CI/CD | AI が書いたコードを、人のレビュー負荷を上げずにどう品質保証してデプロイまで流すか |
| ○ | 障害対応 | 障害時に Claude Code をどう使って調査・修正・ポストモーテムまで回したか |

聞き手は**企業のエンジニア**。「個人でどう便利に使ったか」ではなく「チーム・組織でどう統制し、どう回すか」の文脈で語れることを重視する。

## 2. 進め方の原則

### 2.1 比較実験で仕組みを入れる（Before / After）

一人開発では「痛み」が自然には発生しにくい。そこで、ガードレールや自動化の仕組みは次の手順で導入する。

1. **Before**：仕組みなしで Claude に作業を任せ、起きたことを記録する（ルール違反、テスト漏れ、余計な変更、確認の多さ など）
2. **導入**：仕組みを入れる（CLAUDE.md / permissions / hooks / CI …）
3. **After**：同種の作業をもう一度任せ、差分を記録する

記録は `docs/devlog/` に残し、判断は ADR にする。「入れたらこう変わった」を講義でそのまま見せられる形を目指す。

例外：**シークレット防止と個人情報の除外だけは最初から入れる**（公開リポジトリのため、Before を取ること自体が事故になる）。

**適用時期（ADR-0003）**：走り出しを遅らせないため、Phase 1（MVP）では厳密な Before/After 実験はしない。MVP は普通に Claude Code で作り、気づいたこと（同じ指摘の繰り返し、確認の多さ等）を devlog に残す程度にとどめる。比較実験は MVP 完成後の課題として扱う。

### 2.2 教材化を同時にやる

フェーズの最後にまとめて書くと、詰まった理由を忘れている。以下を作業と同時に残す。

- **開発ログ**（`docs/devlog/`）：セッションごとに「頼んだこと／Claudeの動き／詰まったところ／ルールに足したこと」
- **決定台帳**（`docs/decisions.md`）：すべての決定を1行ずつ。決めた時点で書く
- **ADR**（`docs/adr/`）：選択肢の比較が必要な重い判断のみ（D-008）
- **タスクの状態**（`tasks/`）：会話をまたぐ作業状態。経緯は各タスクの `log/`
- **設定の変更履歴**：CLAUDE.md・`.claude/` の変更は単独コミットにし、育ち方を git 履歴で追えるようにする

### 2.3 一人でチーム運用を再現する工夫

- **PRフローを自分に強制**：Phase 2 以降は main への直接 push 禁止、PR + CI + AIレビュー必須
- **新メンバー役**：まっさらなセッションに CLAUDE.md と docs だけ渡して機能追加させ、迷った箇所をオンボーディングの穴として記録
- **並列開発**：git worktree で複数セッションを同時に走らせ、衝突・調整を体験
- **リモート開発**：スマホからのリモートセッション／クラウドセッションでの開発を前提にし、それ自体を自動化の題材にする
- 可能なら外部の協力者（テスター／PR作成者）を1人巻き込む

### 2.4 安全上の原則

- MVP の「APIキーがフロントに露出する」構成は**一般公開しない**（ローカル or 保護付きプレビューのみ）。公開はサーバー経由化（Phase 2）の後
- 実在の個人名・勤務先・実際の経歴書データはリポジトリに入れない（テストデータは架空の人物で作る）

## 3. フェーズ一覧

| フェーズ | プロダクト | ガードレール | 自動化 / CI/CD | 教材として残すもの |
|---|---|---|---|---|
| 0. 立ち上げ | リポジトリ・ドキュメント整備 | 最小CLAUDE.md、シークレット防止 | — | 開発ログ/ADRの型、「素の状態」の観察 |

| 4. 運用 | 利用者対応・改善 | 監査・コスト管理 | 定期実行、ヘッドレス実行、障害訓練 | ランブック、ポストモーテム |

## 4. フェーズ詳細

### Phase 0：立ち上げ

**プロダクト**
- git リポジトリ作成、GitHub 公開リポジトリ化
- 既存資料を `docs/` に整理（要件定義、プロトタイプ）
- プロトタイプの実データを架空データに差し替え

**ガードレール**
- 最小限の CLAUDE.md（あえて薄くし、Phase 1 の Before 観察に使う）
- `.gitignore` と `permissions.deny` でシークレット・非公開資料を保護

**教材化**
- 開発ログ・ADR のテンプレート
- ADR-0001（進め方）、ADR-0002（公開リポジトリと個人情報）

**完了条件**
- [ ] GitHub に公開リポジトリとして push されている
- [ ] 個人情報・シークレットがリポジトリに含まれていないことを確認済み
- [ ] ロードマップ v0.1 をレビューし合意済み

### Phase 1：MVP

**プロダクト**（詳細は `docs/requirements.md`）
- テキスト貼り付け → Gemini → JSON → RPGステータス画面（基本フロー）
- PDF/docx 入力、ローディング演出、レスポンシブ、エラー表示、プライバシー表記
- スコアリングは「判定はAI、計算は機械」方式（requirements 3.3.1）
- 着手前に決めること：デザイントーン、スキル軸・判定基準（初版は少数の軸で仮置き）、職業判定方針、モデル選定

**ガードレール**

MVP 中は比較実験をしない。ただし既知の工夫（状態ファイル・決定台帳・handoff スキル。`.claude/rules/task-state.md`）はベースとして最初から入れ、その上で起きた困りごとを devlog に残す（D-007）。CLAUDE.md・permissions・hooks を足したときも理由を devlog に1行残す（後の比較実験の材料にする）。

以下の実験は **MVP 完成後の課題**（ADR-0003）。実施時期は MVP 完了時に決める。

| 実験 | Before で観察すること | 導入する仕組み |
|---|---|---|
| E1 規約 | 命名・ディレクトリ・スタイルのブレ、同じ指摘の繰り返し | CLAUDE.md にコーディング規約 |
| E2 権限 | 確認プロンプトの頻度、意図しないコマンド実行 | `permissions` の allow/deny 設計 |
| E3 品質 | テストを通さずに「完了」と言う、lint 違反 | hooks（PostToolUse で format/lint、Stop で test） |
| E4 定型作業 | 開発ログ・ADR 作成の手間、書式のブレ | 共有スラッシュコマンド / skills（`/devlog`, `/adr` など） |

**自動化**
- hooks によるローカルでの自動チェック

**完了条件**
- [ ] 自分の（架空化した）経歴書でステータス画面が表示できる
- [ ] 同じ経歴書を複数回査定して、レベル判定が安定している（基準値は受け入れ基準の議論で決める）
- [ ] 3人以上に触ってもらい「スコアを見るのが楽しいか」の反応を得る
- [ ] E1〜E4 をいつ・どう実施するかが決まっている

### Phase 2：本格化への移行

**プロダクト**
- Gemini 呼び出しをサーバー経由（Vercel Functions 等）に移行し、APIキーをサーバー側管理に
- レート制限対策・リトライ
- 一般公開

**ガードレール**
- ブランチ保護（main 直 push 禁止、CI 必須）
- シークレットスキャン（CI 上）
- 危険操作をブロックする PreToolUse hook

**自動化 / CI/CD**
- GitHub Actions：lint・test・build
- Claude による PR 自動レビュー
- Issue に `@claude` で実装依頼 → PR 作成
- Vercel のプレビューデプロイ / 本番デプロイ

**完了条件**
- [ ] スマホで Issue を立てる → PR が作られる → CI とAIレビューを通る → マージで本番反映、が一通り動く
- [ ] フロントのバンドルに APIキーが含まれていない

### Phase 3：機能拡張

**プロダクト**
- 結果の保存・履歴（DB 導入）、認証
- NPC 対話形式での経歴書作成（Markdown/PDF 出力）

**ガードレール**
- 新メンバー役テスト（まっさらなセッションでのオンボーディング）
- これまでの設定を plugin 化し、別プロジェクトに配布できる形にする
- MCP（DB 等）を使う場合の権限設計

**自動化**
- サブエージェントによる役割分担（実装／テスト／レビュー）
- git worktree による並列開発

**完了条件**
- [ ] 新メンバー役が CLAUDE.md と docs だけで機能追加を完了できる
- [ ] plugin を別リポジトリで読み込んで動作する

### Phase 4：運用

**プロダクト**
- 利用状況を見て改善（クエスト生成＝Phase 3 構想の機能もここで検討）

**ガードレール**
- 監査（Claude が何をしたかの追跡）、コスト管理

**自動化**
- 定期実行（依存更新、週次レポート、エラーログの要約）
- ヘッドレス実行（`claude -p`）を組み込んだスクリプト
- エラー監視

**障害訓練（計画的に発生させる）**
- Gemini レート制限超過 / 不正なJSON応答 / 依存パッケージの脆弱性 / デプロイ起因の本番障害
- それぞれ Claude Code で調査 → 修正 → ポストモーテムまで実施

**完了条件**
- [ ] ランブックとポストモーテムが各1本以上ある
- [ ] 人が張り付かずに回る定期タスクが1つ以上稼働している
